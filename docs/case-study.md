# 案例：五个白纸图标，清缓存全部无效

> 这是 IconDoctor 诞生的那次真实故障。记录得比较细，因为它是 L5（文件夹对象）
> 这一层存在的最好证据。

## 现象

Windows 11（26100），桌面 25 个快捷方式，其中 5 个显示为"白纸 + 快捷方式箭头"：

- 剪映专业版
- Cemu
- 百度网盘
- MuMu模拟器
- DSH Desktop

双击可以正常启动，只是图标不对。其余 20 个图标完全正常。

## 第一轮：标准教程

按网上所有教程做了一遍：

| 操作 | 结果 |
|---|---|
| 结束 explorer，删除全部 `iconcache_*.db`，重启 | ❌ 无效 |
| `ie4uinit.exe -show` | ❌ 无效 |
| 重新注册 ShellExperienceHost（微软官方文档的步骤） | ❌ 无效 |
| 删除并重建这 5 个 `.lnk`（保留目标/参数） | ❌ 无效 |
| 给快捷方式指定外部 `.ico` 文件 | ❌ 无效 |
| 提高 `Max Cached Icons` 到 8192 | ❌ 无效（但值得保留） |

到这里，教程能提供的所有手段都用完了。

## 第二轮：分层隔离

不猜了，改成控制变量。所有结论都来自同一条命令：用 `SHGetFileInfo` 取图标，
再从目标 exe 用 `ExtractIconEx` 取基准，对比"shell 画的"和"本该有的"。

| 实验 | 结果 |
|---|---|
| 直接对 `Cemu.exe` 取图标 | ✅ 正确（蓝色 C） |
| 对 `Cemu.lnk` 取图标 | ❌ 白纸 |
| 把一个**正常的** `Code.lnk` 复制进桌面目录 | ❌ 变白纸 |
| 同一个 `Code.lnk` 复制到 `E:\` 根目录 | ✅ 正常 |
| 同一个 `Code.lnk` 复制到 `E:\TestDir` | ✅ 正常 |
| 在桌面目录**新建**指向 `notepad.exe` 的快捷方式 | ❌ 白纸 |
| 把 `Cemu.exe` 本体放进桌面目录 | ✅ 图标正常 |
| 桌面目录里放一个 `.url` 文件 | ✅ 图标正常 |

结论收敛得非常干净：

- 不是 exe 没图标（exe 自己取得到）；
- 不是 `.lnk` 内容坏了（复制正常人做的 `.lnk` 进来也白）；
- 不是缓存（清了一整轮）；
- 不是驱动/路径（同盘不同目录结果不同）；
- **只有"这个目录里的 `.lnk`"不工作**，`.exe` 和 `.url` 都正常。

## 第三轮：确认是"文件夹对象"而非"注册"

把桌面临时指向一个全新目录 `E:\Probe1`（`SHSetKnownFolderPath`），重启 explorer：

- 新目录里新建的 `.lnk` → ✅ 图标正常

排除"桌面被重定向"这件事本身。再排除两个常见嫌疑：

- 删掉 `desktop.ini`、去掉目录只读属性 → ❌ 仍然白
- 清理 ACL（一条 `Everyone` 的 Deny + 一条孤儿 SID `S-1-4-*`）→ ❌ 仍然白

也就是说：**同一个路径、同样的权限、同样的内容，换成新的目录对象就好了**。
旧目录对象本身带着某种损坏状态，而 shell 在解析目录内 `.lnk` 图标时会命中它。

## 修复

同卷内"换壳"（改名，不复制数据，瞬间完成）：

1. 新建 `E:\DeskTop_new`
2. 把 `E:\DeskTop` 的 59 个条目移进去
3. 旧目录（已空）改名为 `E:\DeskTop_old`
4. `E:\DeskTop_new` 改名为 `E:\DeskTop`
5. 重启 explorer，清一次图标缓存，重建那 5 个快捷方式

结果：5 个图标全部恢复，路径没变（项目目录、脚本里的绝对路径都不受影响）。

## 可复用的判据

这次故障最值钱的不是"怎么修"，而是**怎么判定**：

> 同一份 `.lnk`，放进目标目录渲染为白纸，放进 `%TEMP%` 渲染正常
> ⇒ 问题在目录对象，不在图标、不在快捷方式、不在缓存。

这条判据已经固化成 `Test-LayerFolderObject`（L5 探针），
每次诊断都会自动跑一遍。

## 附：同一天的第二种病因 —— 快捷方式数据失效

上午修完文件夹对象后，下午重启电脑，**25 个快捷方式集体变白**（连上午正常的
VS Code、IDEA、微信都白了）。看起来像复发，但探针给出了完全不同的结论：

| 实验 | 结果 | 推论 |
|---|---|---|
| `%TEMP%` 里新建快捷方式 | ✅ 图标正常 | 系统图标处理器没坏 |
| **桌面上**新建快捷方式 | ✅ 图标正常 | **文件夹没坏** |
| 桌面上**已有的**快捷方式 | ❌ 全部 28 色（白纸） | **坏的是文件本身** |
| 重建其中一个 `.lnk` | ✅ 恢复正常 | 证实 |

对比文件头能看出差异：

```
损坏的 .lnk：LinkFlags = 0x0000009B   （含 HasRelativePath + HasWorkingDir）
新建的 .lnk：LinkFlags = 0x00000083
```

这些快捷方式是几个月前创建的，内部存了一条**相对路径**。目录被"换壳"重建后，
相对路径的基准变了，重启后解析失败，shell 就回退成通用白图标——但 `LinkInfo`
里的 `TargetPath` 字符串仍然有效，所以**双击依然能正常启动**。

修复：重建 `.lnk`（保留参数、工作目录、描述），24 个一次性修完：

```powershell
Invoke-IconRepair
```

### 两次故障的对照

| | 上午 | 下午 |
|---|---|---|
| 病因 | 文件夹对象损坏 | 快捷方式内的链接数据失效 |
| 判据 | 同文件在桌面白、在 %TEMP% 正常 | 同目录里新建正常、已有文件白 |
| 修复 | 目录换壳重建 | 逐个重建快捷方式 |
| 诊断层 | L5 | L2 |

> **同样是白纸图标，病因可以差两层。** 这正是把"清缓存"当成唯一答案的教程
> 会失效的地方：它既修不好 L5，也修不好 L2。
